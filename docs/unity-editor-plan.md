# План: редактор, который выглядит и работает как Unity

Составлен 2026-10-09, после этапов 0–5 (`implementation-plan.md`). Заменяет этапы 6–13 того
документа. Как редактор связан с движком и ScenarioCreator — в `integration-plan.md`.

Пути кода — относительно `app/src/app/`.

---

## 0. Решения, под которые написан план

| # | Вопрос | Решение (2026-10-09) |
|---|---|---|
| 1 | Языки интерфейса | Украинский и английский. Русский не нужен |
| 2 | Ключ публикации | Отдельный, не общий `ADMIN_TOKEN` (§7) |
| 3 | Скрипты | И то и другое: преподаватель пишет код в редакторе **и** берёт готовые поведения из библиотеки (§3.2) |
| 4 | Образец | Редактор Unity: расположение, названия, поведение, клавиши |

Раньше принятые решения остаются: проект — папка на компьютере пользователя; редактор
открывается с сайта платформы; сценарий — сцена плюс скрипты, `Scenario.ts` остаётся.

**Решение 4 отменяет одно прежнее.** Было: Play запускает сценарий в iframe из ZIP. В Unity Play
идёт внутри редактора: окно Game рядом со Scene, Hierarchy и Inspector показывают живую сцену.
Поэтому Play переезжает внутрь редактора, а запуск из ZIP становится тем, чем он является в
Unity, — «Build And Run» (§3.1).

## 1. Что значит «как в Unity»

**Правило.** Когда есть выбор, как назвать, куда поставить или как должно себя вести — делаем
как в редакторе Unity 6 в раскладке Default. Отступаем только там, где это невозможно (§2), и
каждое отступление записано.

**Мера.** Таблицы паритета в §5: по строке на возможность Unity, с колонками «сейчас» и «этап».
Этап закрыт, когда его строки проверены — автоматической проверкой (`npm run e2e`) там, где её
можно написать, и глазами по списку там, где нельзя.

**Три уровня, по убыванию обязательности:**

- **Ядро** — то, без чего не похоже на Unity вообще: навигация в сцене, инструменты, Hierarchy,
  Inspector, Project, Console, Play. Этапы 6–13.
- **Рабочий процесс** — то, чем пользуются каждый день, но без чего первый сценарий собрать
  можно: префабы, окна настроек, история отмен. Этапы 14–16.
- **Специальные окна** — Animation, Animator, инструменты UI, Profiler и прочее. §6, «после».

## 2. Что не будет таким же, и почему

Честный список. Его стоит прочитать до остального: «всё как в Unity» в браузере и на этом
движке имеет границы.

**Браузер не отдаёт:**

| В Unity | В редакторе | Причина |
|---|---|---|
| `Ctrl+N` новая сцена, `Ctrl+Shift+N` пустой объект | Без клавиши / `Alt+Shift+N` | Chrome открывает окно и окно инкогнито, страница перехватить не может |
| `Ctrl+1…9` — переключение окон | Только мышью и через меню Window | Chrome переключает вкладки браузера |
| `Ctrl+W`, `Ctrl+T`, `Ctrl+Tab` | Нет | Закрытие и переключение вкладок браузера |
| Плавающие окна на втором мониторе | Только вкладки внутри окна | Отдельное окно браузера — отдельная страница |
| Двойной клик по скрипту открывает Visual Studio / Rider | Открывает встроенный редактор кода | Страница не знает полного пути к файлу и не может запускать программы |
| «Show in Explorer» | Нет | То же |
| Проект открывается сам при запуске | Один клик на стартовом экране | Доступ к папке браузер даёт только по жесту |

Остальные клавиши Unity работают: `Ctrl+P` Play, `Ctrl+S`, `Ctrl+D`, `Ctrl+Z / Y`, `Q W E R T Y`,
`F`, `F2`, `Del`, `Ctrl+A`, `Ctrl+F`, `Ctrl+Shift+F`.

**Движка нет — нет и окна.** В WebEngineTS отсутствуют, и план их не добавляет: Terrain,
NavMesh, Tilemap, Timeline, Shader Graph, VFX Graph, запекание света, Occlusion Culling,
флаг Static и статический батчинг из инспектора. Package Manager, Asset Store, сервисы Unity,
сборка под платформы — не имеют смысла: «платформа» одна, каталог.

**Язык скриптов — TypeScript, не C#.** `MonoBehaviour` → `ScriptableBehaviour`,
`[SerializeField]` → `@SerializedField()`. Публичное поле без декоратора в инспектор не попадёт:
у TypeScript нет сведений о типах во время выполнения, и движок их берёт из декораторов.

**Объём.** Unity делали сотни людей двадцать лет. Этот план даёт ядро и рабочий процесс —
около восьми месяцев одного человека (§8). «Специальные окна» — сверх этого.

## 3. Что придётся построить иначе, чем сейчас

Пять решений в устройстве редактора, без которых отдельные возможности Unity не сложатся.

### 3.1 Play внутри редактора, Build And Run — отдельно

Как в Unity, запусков два:

| | Play (`Ctrl+P`) | Build And Run |
|---|---|---|
| Где идёт | Вкладка Game в редакторе | Отдельная вкладка/iframe |
| На чём | Движок редактора | Бандл движка платформы — тот же файл, что у студентов |
| Hierarchy / Inspector | Живые, показывают играющую сцену | Нет |
| Для чего | Быстро проверить | Убедиться, что студент увидит то же |

**Play устроен так.** Редактор собирает сценарий в ZIP в памяти и отдаёт его настоящему
загрузчику движка (`Application.loadScenarioFromBuffer`) — в своей же странице. Загрузчик создаёт
для сценария *новую* сцену, поэтому сцена редактирования не трогается вообще: её не нужно
сохранять в снимок и восстанавливать. Stop выгружает сценарий и возвращает сцену редактирования
активной. Правило Unity «изменения в Play пропадают» получается само.

Что это требует:

- Скрипты сценария импортируют `"WebEngineTS"`; в редакторе это должен быть **тот же экземпляр
  движка**, что у самого редактора, иначе у сценария окажется свой `SceneManager` и панели его
  не увидят. Решение: import map в `index.html` редактора ведёт `"WebEngineTS"` на файл-прокладку,
  который переэкспортирует экземпляр редактора. Список экспортов прокладки генерируется при
  сборке из бандла движка.
- Классы скриптов загружаются дважды — для режима редактирования и для Play. Реестр типов
  движка вторую регистрацию под тем же именем отклоняет. Нужен запрос к движку E4.
- В режиме редактирования скрипты не должны выполняться. Запрос E2.
- `Application` подгоняет рендер под окно браузера; в редакторе канвас — вкладка. Проверить
  спайком, возможно понадобится правка в движке.

Нынешний `play-mode.service.ts` (своя урезанная копия игрового цикла) удаляется.

**Спайк перед этапом 13** (2–3 дня): один и тот же `THREE.Scene` рисуют два рендерера —
вьюпорт редактора и движок во вкладке Game. В three.js это разрешено, но видеопамять
удваивается, и надо убедиться, что материалы движка это переносят.

### 3.2 Скрипты: редактор кода и библиотека готовых

**Редактор кода.** Вкладка Code — Monaco (тот же редактор, что в VS Code): подсветка,
автодополнение и ошибки по типам движка (`WebEngineTS.d.ts` подключается как библиотека).
Двойной клик по скрипту в Project открывает его здесь; `Ctrl+S` сохраняет в папку проекта и
компилирует.

**Компиляция.** TypeScript → JavaScript делает языковой сервис Monaco (его рабочий поток умеет
и проверять, и выдавать JS). Это меняет прежний план: esbuild-wasm не нужен, а значит
политику безопасности платформы ослаблять (`'wasm-unsafe-eval'`) не придётся. Что сам Monaco
работает под CSP платформы без послаблений, проверяется первым делом в этапе 10.

**Перезагрузка скриптов** — как domain reload в Unity: скомпилировалось → сцена сериализуется →
классы заменяются → сцена восстанавливается. Ошибки компиляции идут в Console со ссылкой на
строку и блокируют Play с тем же сообщением, что в Unity.

**Библиотека готовых поведений.** Add Component → Library: Rotator, Orbiter, Oscillator,
LookAt, Follow, Billboard, ClickToggle, ShowOnClick, OrbitCamera, Timer и т. п. При первом
добавлении исходник **копируется** в `scripts/library/` проекта. Так проект остаётся
самодостаточным и собирается ScenarioCreator без редактора, а преподаватель может открыть
файл, посмотреть, как сделано, и изменить — это и есть мост от «собираю из готового» к «пишу сам».

**Внешний редактор остаётся.** Кто хочет писать в WebStorm — пишет: редактор перечитывает
папку при возврате в окно и перекомпилирует.

### 3.3 Ассеты с собственным идентификатором

В Unity файл можно переименовать и перенести — ссылки не рвутся, потому что рядом лежит
`.meta` с GUID. Сейчас идентификатор ассета — хеш от пути (`ScenarioCreator/scenario-meta.mjs`),
и переименование его меняет.

- Редактор пишет рядом с каждым ассетом `<файл>.meta` (JSON: `guid`, позже — настройки импорта).
- **ScenarioCreator** берёт `guid` из `.meta`, если он есть, иначе считает как раньше. Это
  изменение контракта между репозиториями; десять существующих сценариев без `.meta` не
  затрагиваются.
- Материалы, префабы, физические материалы становятся файлами (`.mat.json`, `.prefab.json`),
  а не значениями внутри сцены. Запрос к движку E5.

### 3.4 Окна-вкладки и раскладки

Unity — это вкладки, которые перетаскиваются между областями. Сейчас панели прибиты.

- **Этап 11:** четыре области (лево, центр, право, низ), вкладки перетаскиваются между ними,
  закрываются и открываются из меню Window, `Shift+Space` разворачивает на весь экран, готовые
  раскладки (Default, 2 by 3, Tall, Wide), своя раскладка сохраняется. Так устроен и макет
  (`design/wets/layout.jsx`).
- **Позже:** произвольное деление областей, как в Unity.
- **Не будет:** плавающих окон (§2).

### 3.5 Чем рисуется Scene

Сейчас вьюпорт рисует сцену собственным рендерером three.js, минуя движок. Поэтому в Scene не
видно того, что движок обновляет в своём цикле: линий, частиц, UI, LOD, постобработки.

- **До этапа 13** так и остаётся; редактор сам дорисовывает значки и каркасы компонентов.
- **Этап 13** даёт вкладку Game через движок. Сделать и Scene через движок (камера редактора,
  рендер в цель) — запрос E8, он же `RenderTexture` из общего плана (§1.3 там).

## 6. Этапы

Порядок выбран так, чтобы польза появлялась рано: после этапа 10 сценарий без кода проходит весь
путь до каталога в инструментах, которые ведут себя как в Unity.

### Этап 6 — сцена и объекты (≈2 недели)

1. **3D Object.** GameObject → 3D Object → Cube, Sphere, Capsule, Cylinder, Plane, Quad
   (фабрики `Mesh.create*` движка) с `MeshFilter`, `MeshRenderer` и материалом по умолчанию.
   То же в «+» Hierarchy. Новый объект встаёт перед камерой редактора и выбран.
2. **Навигация как в Unity.** Свой контроллер камеры вместо `OrbitControls`: ЛКМ — выбор и
   рамка; `Alt`+ЛКМ — орбита; ПКМ — осмотр, с `WASD/QE` полёт, `Shift` быстрее; СКМ — панорама;
   колесо — зум; `F` и `Shift+F`.
3. **Куб ориентации** (`ViewHelper` из three.js): клик по оси — вид вдоль неё, клик по центру —
   перспектива / изометрия.
4. **Инструменты.** `Q` рука, `Y` комбинированный; Pivot / Center и Local / Global работают;
   привязка — при зажатом `Ctrl` или включённой кнопкой, шаг — из настроек.
5. **Выбор.** Оранжевый контур; рамка; `Ctrl` и `Shift` в сцене.
6. **Значки и каркасы компонентов** силами редактора: свет (направление, радиус, конус),
   камера (пирамида видимости), коллайдеры, источник звука. Меню Gizmos: что показывать.
7. **Освещение сцены.** Переключатель, как в Unity; по умолчанию включается, когда в сцене есть
   свет. Shaded / Wireframe. Сетка: показать, шаг.

*Готово, когда:* человек, работавший в Unity, вращает, летает, выбирает и двигает объекты, не
переучиваясь; куб из меню виден на платформе после сборки.

### Этап 7 — Hierarchy (≈1 неделя; E7)

Раскрытие и сворачивание (состояние хранится в `.editor/`); перетаскивание между строк с линией
вставки; полное контекстное меню; клавиатура; `Alt+Shift+N` — пустой ребёнок; поиск `t:`;
серые неактивные; глаз и палец; двойной клик — показать; значок по главному компоненту.

*Готово, когда:* дерево из тридцати объектов перестраивается перетаскиванием и клавиатурой так
же, как в Unity, и порядок детей сохраняется в сцене.

### Этап 8 — Inspector (≈2.5 недели; E7)

1. **Шапка.** Галочка активности (`setActive`); Tag и Layer — выпадающие списки с
   «Add Tag… / Add Layer…». Имена тегов и слоёв — файл проекта `ProjectSettings/TagManager.json`.
2. **Transform.** Reset, Copy / Paste; протяжка за подпись; углы Эйлера без скачков.
3. **Компоненты.** Сворачивание запоминается; галочка включения (`Behaviour.enabled`);
   всё меню компонента работает. Add Component строится из реестра типов движка с его
   категориями — ручной список `BUILTINS` удаляется.
4. **Редакторы полей** для всех `FieldType`: число с протяжкой, ползунок для `@Range`, флаг,
   строка, enum, `Vector2/3/4`, поворот, цвет (окно выбора с альфой), `Rect`, `Bounds`,
   ссылки на объект / компонент / ассет (перетаскивание, окно выбора, подсветка цели), `Sprite`,
   `Mesh`, кривая, градиент, массив со сменой порядка, вложенная структура, `@Header`,
   `@Tooltip`.
5. **Несколько объектов:** общие компоненты и поля, «—» при разных значениях.

*Готово, когда:* каждый сериализуемый компонент движка (их 44) настраивается в инспекторе
целиком, и в коде инспектора нет ни одного имени компонента.

### Этап 9 — Project и ассеты (≈3 недели; E3, E5; ScenarioCreator)

1. **`.meta` с GUID** (§3.3) и правка ScenarioCreator. Проверка: сцена ссылается на текстуру,
   текстуру переименовали, ссылка жива — в редакторе и после сборки.
2. **Источник ассетов** поверх папки проекта (`Resources.useSource`): текстуры и модели видны в
   сцене редактора.
3. **Окно Project:** Create (Folder, Scene, Material), `F2`, `Ctrl+D`, перенос, поиск, значки /
   список, миниатюры материалов и моделей.
4. **Материал как файл.** Инспектор материала; у рендерера материал показан внизу инспектора.
5. **Перетаскивание:** модель в сцену, текстура на объект (создаёт материал), ассет в поле.
6. **Инспектор ассета:** превью текстуры, модели, прослушивание звука.

*Готово, когда:* сцена с текстурированной моделью и общим на два объекта материалом собрана
перетаскиванием и выглядит на платформе так же.

### Этап 10 — Build, Build And Run, Publish (≈2 недели + платформа ≈1 неделя)

1. **Компилятор TypeScript в браузере** (без окна редактора кода — оно в этапе 12): ZIP
   нуждается в скомпилированном `Scenario.ts`.
2. **Упаковщик:** проект → ZIP в памяти, по тем же правилам, что `build-package.mjs`.
   `npm run e2e:build` дополняется сравнением манифестов двух сборщиков.
3. **File → Build Settings:** сцены в сборке, стартовая сцена (пишется как `entryScene`).
4. **Build** — ZIP файлом. **Build And Run** — ZIP во вкладке на бандле движка платформы.
   До этапа 13 кнопка Play делает то же.
5. **Publish** (§7): проверка сценария → ключ → отправка. Проверки: есть камера, есть свет,
   известны все типы компонентов, заполнены название и адрес.
6. **Платформа:** ключи публикации (§7).

*Готово, когда:* преподаватель со своим ключом публикует сценарий из редактора, он появляется
в `/admin` скрытым, и его ключом нельзя удалить или опубликовать чужое.

> **Веха 1.** Сценарий без кода — от «Создать проект» до каталога. ≈11 недель редактора,
> ≈3 недели движка (E3, E5, E7), ≈1 неделя платформы.

### Этап 12 — скрипты (≈3.5 недели; E2, E4, E6)

## 7. Ключ публикации (платформа, `testv/virtual-lab`)

Сейчас запись в каталог защищает один `ADMIN_TOKEN`: кто его знает, может удалять и
публиковать что угодно. Преподавателю его давать нельзя.

**Ключи авторов.** Не один «ключ публикации», а по ключу на человека: тогда видно, кто что
загрузил, и ключ можно отозвать, не меняя остальным.

- **База** (миграция `006`): таблица `publish_keys` — `id`, `label` (чей), `token_hash`,
  `created_at`, `last_used_at`, `revoked_at`; в `scenarios` — столбец `owner_key_id`.
  В базе лежит только SHA-256 ключа; сам ключ показывается один раз при выдаче.
- **Права ключа автора:**

  | Действие | Ключ автора | `ADMIN_TOKEN` |
  |---|---|---|
  | Создать сценарий | Да — всегда скрытым, владельцем становится ключ | Да |
  | Изменить описание, обложку, версию своего сценария | Да | Да |
  | Загрузить архив в свой **скрытый** сценарий | Да | Да |
  | Загрузить архив в **опубликованный** сценарий | Нет (см. ниже) | Да |
  | Опубликовать, скрыть, удалить | Нет | Да |
  | Трогать чужие сценарии; хранилище; телеметрия | Нет | Да |

- **`/admin`:** раздел «Ключи авторов» — выдать (с подписью, чей), список с датой последнего
  использования, отозвать. У сценария виден владелец.
- **Редактор:** ключ вводится в диалоге Publish, хранится до закрытия вкладки; галочка
  «запомнить на этом компьютере».
- Ограничение частоты запросов, строка в журнале на каждое действие ключа, тесты в `backend`
  и `e2e`.

**Обновление уже опубликованного сценария — решение за вами.** Архив, загруженный в
опубликованный сценарий, студенты увидели бы сразу, без проверки. Варианты:

1. **Запретить** (рекомендую начать с этого): ключ автора получает отказ с объяснением;
   обновление проводит администратор. Просто, без новых экранов.
2. **Черновик:** архив ложится рядом как «ожидающий», администратор в `/admin` нажимает
   «принять». Удобнее авторам; это ещё один столбец, экран и ≈3–4 дня.

## 9. Как проверяется

- **`npm run e2e`** — каждый этап добавляет сценарии; гонять на собранном бандле, не на
  `ng serve` (этап 3 показал, что они расходятся).
- **`npm run e2e:build`** — проект из редактора собирается ScenarioCreator и запускается в
  движке; с этапа 10 сравнивает ещё и два сборщика.
- **Список глазами** — то, что автоматически не проверить: ощущение навигации, перетаскивание,
  системный диалог выбора папки, вид в светлой теме. По строкам таблиц §5.
- **Каждый этап заканчивается сценарием для каталога**, собранным только возможностями этого
  этапа. Не собирается — этап не закрыт.
