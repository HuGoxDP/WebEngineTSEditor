## 1. Что есть сейчас

**Движок (WebEngineTS)** — к редактору готов больше, чем редактор им пользуется:

- `SceneSerializer` сохраняет и загружает все встроенные компоненты, со ссылками на GameObject,
  компоненты и ассеты; материалы лежат в таблице `assets` внутри сцены.
- 47 файлов с `@Serializable({ typeName, category })` — метаданные для инспектора уже есть
  (`getAllFields`, `FieldMeta`: тип, range, header, tooltip, enum, assetType).
- `AssetDatabase` (guid ↔ путь ↔ объект), `Resources.useSource(IAssetSource)` — публичные.
- `Prefab`, `PrefabDiff`, варианты — готовы.
- **Не готово:** `IScenarioManifest.entryScene` объявлен, но загрузчик его не читает
  (`ScenarioTypes.ts:124`). Режима редактирования нет.

**ScenarioCreator** — 10 сценариев, все процедурные: мир строится кодом в `Scenario.ts`.
Сборка: `tsc` → `manifest.json` → копия `assets/` → ZIP. Сцен в JSON нет ни в одном сценарии,
`@SerializedField` не использует ни один скрипт.

**Редактор** — собирается; иерархия, вьюпорт с гизмо, undo на снимках, сохранение сцены
скачиванием JSON. Но:

- Инспектор написан руками (`component-section.component.ts`), метаданные движка не читает.
- `ComponentRegistryService.BUILTINS` — ручной список с устаревшим комментарием «встроенные
  компоненты не декорированы».
- Панель Project — заглушка с выдуманными файлами.
- Play mode — своя урезанная копия игрового цикла (`play-mode.service.ts`): без частиц, аудио,
  UI, плагинов, сброса ввода. Расходится с `Application._loop`.
- Вьюпорт рисует `_internalThreeScene` собственным `THREE.WebGLRenderer`, мимо `RenderBackend`.
- Движок вшит в бандл Angular, а платформа берёт его через import map
  (`WebEngineTS.standalone.js` + `externalDependencies`).

**Вывод:** три части сейчас не связаны ничем. Редактор пишет JSON, который никто не читает;
ScenarioCreator собирает код, который редактор не видит.

## 2. Как их связать: два контракта

```
        WebEngineTS (движок)
        │  метаданные типов, SceneSerializer, AssetDatabase, загрузчик сценариев
        ▼
   ┌─────────────┐   папка проекта сценария    ┌──────────────────┐   ZIP    ┌──────────┐
   │  Редактор   │ ◄─────────────────────────► │ ScenarioCreator  │ ───────► │ платформа│
   └─────────────┘   (общая, на диске)         └──────────────────┘          └──────────┘
```

**Контракт А — папка проекта.** Редактор открывает ту же папку, которую уже собирает
ScenarioCreator, и добавляет в неё сцены:

```
Scenarios/<Name>/
├── scripts/                  # TS, пишется в WebStorm; ровно один ScenarioBehaviour
│   ├── Scenario.ts
│   └── components/           # ScriptableBehaviour с @Serializable — их вешает редактор
├── assets/
│   ├── scenes/main.scene.json   # ← пишет редактор (SerializedScene)
│   ├── textures/ models/ audio/
├── scenario.meta.json        # ← редактор получает форму для этого файла
└── .editor/                  # камера редактора, раскладка; в ZIP не попадает
```

Сцена лежит в `assets/scenes/`, а не в `scenes/` в корне, по трём причинам: сборщик уже копирует
`assets/` целиком, сцена получает guid как любой ассет, и она читается через `IAssetSource`
одинаково из ZIP и из стримингового манифеста. Менять `build-manifest.mjs` не нужно.

**Контракт Б — ZIP.** Не меняется. В манифест добавляется только необязательный `entryScene`.
`archive-validation.js` платформы проверяет пять полей и наличие entry-скрипта, поэтому
платформу трогать не нужно, а десять существующих сценариев работают как раньше.

**Модель сценария — гибрид.** Статика (объекты, свет, камеры, материалы, UI) — в сцене.
Поведение — в скриптах-компонентах, навешанных в редакторе. `ScenarioBehaviour` остаётся:
запускается после загрузки сцены и делает то, что удобнее кодом (118 элементов таблицы
Менделеева руками никто расставлять не будет).

## 3. Развёртывание: Docker, рядом с каталогом

Требование (2026-10-07): редактор запускается через Docker вместе с платформой.

```
browser → nginx :80 ─┬─ /            → каталог (Angular SPA)          как сейчас
                     ├─ /editor/     → editor:80 (статика редактора)  ← новое
                     ├─ /scenarios/* → том архивов                    как сейчас
                     └─ /api/*       → backend:3000                   как сейчас
```

**Один origin, путь `/editor/`.** Это даёт три вещи без новой инфраструктуры:

- **Publish прямо в каталог.** Редактор зовёт уже существующие `POST /api/catalog` и
  `POST /api/scenarios/:id/archive` с `ADMIN_TOKEN`. CSP платформы разрешает только
  `connect-src 'self'`, поэтому отдельный порт или домен потребовал бы её ослаблять.
- **Проверку архива делает бэкенд** (`archive-validation.js`) — второй копии правил в редакторе
  не нужно.
- **Play на том же движке, что у студентов**: iframe редактора берёт
  `/assets/WebEngineTS.standalone.js` платформы — буквально тот же файл.

**Как собирается.**

- В этом репозитории: `Dockerfile` (сборка Angular с `--base-href /editor/` → `nginx:alpine`) и
  свой минимальный `nginx.conf`. Образ самодостаточен: `docker build` работает без платформы.
  Тарболл движка уже лежит в `app/` и коммитится, как у платформы.
- В `testv/virtual-lab`: сервис `editor` в **отдельном** `docker-compose.editor.yml`
  (`build.context: ../../WebEngineTSEditor`) и `location ^~ /editor/` в `nginx/nginx.conf`.
  Отдельный файл — чтобы базовый стек платформы и её CI собирались без репозитория редактора:
  платформой пользуются студенты, и её сборка не должна зависеть от недоделанного редактора.
  Запуск: `docker compose -f docker-compose.yml -f docker-compose.editor.yml up --build -d`.

**Что это ломает или требует — проверено по `nginx.conf` и `csp.conf`:**

| Что | Почему | Что делать |
|---|---|---|
| Import map редактора | CSP пускает инлайн-скрипт только с nonce, nginx штампует его через `sub_filter` | Проксировать `/editor/` с `proxy_set_header Accept-Encoding ""` (иначе `sub_filter` не видит сжатый ответ) и не сжимать в контейнере редактора |
| Компиляция TS в браузере (фаза 5) | esbuild-wasm требует `'wasm-unsafe-eval'`, в CSP его нет намеренно | Отдельная CSP только для `location /editor/`; страницы студентов не ослаблять |
| Заголовки в новом `location` | `add_header` не наследуется | Повторить блок заголовков и `include csp.conf`, как в остальных; e2e `csp.spec.ts` это проверяет |
| Работа с локальной папкой | File System Access API есть только в secure context: `localhost` или HTTPS | На `localhost` работает. На сервере по голому HTTP — нет; см. решение 6 ниже |
| Доступ | `/editor/` увидит любой, кто знает адрес | Писать без токена редактор никуда не может. Токен — как в `/admin`, в `sessionStorage`. При желании — basic auth в nginx |
| Экран входа платформы | Пользователей и ролей в платформе нет, только один `ADMIN_TOKEN` | Редактор живёт с этим же токеном; роли — отдельная задача платформы |

**Где хранятся проекты** — главный вопрос, который поднимает Docker. Редактор в контейнере — это
статика; файлы проекта он сам не хранит. Два варианта:

- **А. Локальная папка** (как в §2): автор открывает `ScenarioCreator/Scenarios/<Name>` у себя,
  скрипты пишет в WebStorm, в каталог уходит только готовый ZIP. Работает сегодня, бэкенд не
  меняется. Пользоваться может только тот, у кого есть папка проекта.
- **Б. Хранение на сервере**: новые эндпоинты `/api/editor/projects/*` и том
  `virtual_lab_projects`. Редактором можно пользоваться с любой машины, но это новый код в
  живой платформе, и скрипты из WebStorm туда сами не попадут.

**Решено 2026-10-07: файлы проекта лежат на компьютере пользователя.** Редактор открывается с
сайта, им пользуются преподаватели, но в Docker хранятся только опубликованные сценарии — ни
проектов, ни исходников на сервере нет. Это вариант А по хранению при аудитории варианта Б;
серверное хранилище проектов из плана убрано.

Сделано: `ProjectService` (`app/src/app/services/project.service.ts`) — папка через File System
Access API, handle запоминается в IndexedDB, после перезагрузки браузер просит один клик для
повторного доступа. Панель Project показывает настоящую папку.

**Что из этого следует:**

- **HTTPS на боевом сервере обязателен.** File System Access API работает только на `localhost`
  или по HTTPS; по обычному HTTP с другого компьютера панель покажет «недоступно в этом
  браузере». Плюс `ADMIN_TOKEN` при публикации иначе идёт открытым текстом.
- **Только Chrome и Edge.** В Firefox и Safari этого API нет.
- **Проект привязан к компьютеру.** С другой машины его не открыть, резервных копий на сервере
  нет: потерял папку — остался только опубликованный ZIP, а из него проект не восстановить.
  Стоит позже дать «скачать проект архивом».
- **Скрипты.** Преподаватель вряд ли пишет TypeScript. Предлагаю: сцены собираются из
  компонентов движка и из библиотеки готовых скриптов (`Rotator`, `Orbiter` и т. п.), которую
  пишет разработчик; редактор кода в браузере — позже и отдельно. Это нужно подтвердить.
- **Один общий токен на всех, кто публикует.** Кто что опубликовал — не видно, отозвать доступ
  одному нельзя. Пользователи и роли — отдельная задача платформы.

## 4. Решения, которые нужны от тебя

Это ответ на «P1 — для чего редактор» из общего плана. Мои рекомендации — первый вариант в
каждой строке; фазы ниже написаны под них.

| # | Вопрос | Рекомендую | Альтернатива |
|---|---|---|---|
| 1 | Модель сценария | Гибрид: сцена + скрипты, entry point остаётся | Только сцена, без `Scenario.ts` — ломает 10 сценариев |
| 2 | Где живут проекты | Прямо в `ScenarioCreator/Scenarios/` | Отдельная папка + импорт/экспорт |
| 3 | Play | iframe с настоящим `Application` и ZIP, собранным в памяти | Играть на месте, в сцене редактора (как сейчас) |
| 4 | Где пишутся скрипты | В WebStorm; редактор следит за папкой | Встроенный редактор кода |
| 5 | Браузер | Только Chromium (нужен File System Access API) | Все браузеры — тогда без прямой работы с папкой |
| 6 | Кто пользуется редактором и где файлы | Преподаватели через сайт, файлы проекта на их компьютере | Хранение проектов на сервере — отклонено: в Docker только сценарии |
| 7 | Как редактор попадает в стек платформы | Отдельный `docker-compose.editor.yml` | Сервис прямо в основном `docker-compose.yml` — проще запуск, но сборка платформы начинает зависеть от этого репозитория |

**Решено:** 6 — преподаватели через сайт, файлы проекта на их компьютере (§3); 7 — отдельный compose-файл (сделано).
Остальные пока идут по рекомендациям. Пункт 4 из-за решения 6 требует пересмотра — см. §3,
«Скрипты».

## 5. Фазы

Оценки — для одного человека, грубые.

### Фаза 0 — проверить фундамент (0.5–1 день)

1. Открыть редактор в браузере и снять скриншот через `WebEngineTS/scripts/shoot.mjs`
   (общий план §3.2: сборка проходит, запуск в браузере не проверен).
2. Закоммитить висящие `app/WebEngineTS-0.1.0.tgz` и `package-lock.json`.
3. Дымовой round-trip: куб + свет + камера → Save → New → Open → сравнить JSON.
4. Проверить гизмо и выбор кликом после исправления зеркальности (2026-09-04): вьюпорт написан
   до него.

*Готово, когда:* редактор открывается без ошибок в консоли и сцена из трёх объектов
переживает сохранение и загрузку.

### Фаза 1 — сквозной срез «редактор → ZIP → платформа» (5–7 дней) ⭐ начать здесь

Цель — самая тонкая нить через все три части, сразу в Docker. **Изменений в движке не требует.**

1. **Спайк: один экземпляр движка** (первым, он определяет сборку). Перевести редактор на
   `externalDependencies` + import map, как у платформы. Взять её standalone-бандл напрямую
   нельзя: three зашит внутрь и спрятан, а вьюпорту нужны `OrbitControls`, `TransformControls`
   и `Raycaster` из того же экземпляра three, что у движка. Кандидат: в import map редактора
   `"WebEngineTS"` → `WebEngineTS.esm.js` (three у него peer-зависимость), `"three"` и
   `"three/addons/"` → файлы three. Проверить, что esm-сборка не тянет другие внешние модули
   (`cannon-es`, `jszip`). *Критерий:* на странице один three, гизмо работает. Play-iframe при
   этом берёт standalone платформы (фаза 6).
2. **Docker** (§3): `Dockerfile` + `nginx.conf` здесь, `--base-href /editor/`;
   `docker-compose.editor.yml` и `location ^~ /editor/` в `testv/virtual-lab`. Проверить, что
   import map получает nonce и в консоли нет нарушений CSP. Прогнать `e2e` платформы — каталог
   не должен заметить соседа.
3. **`ProjectStore` / `FsProjectStore`**: открыть папку через `showDirectoryPicker`, прочитать
   `scenario.meta.json`, перечислить `assets/` и `scripts/`, хранить handle в IndexedDB
   (недавние проекты).
4. **Save/Open** пишут и читают `assets/scenes/main.scene.json` в папке проекта вместо
   скачивания файла.
5. **«New Scenario»**: создаёт раскладку папки и шаблонный `scripts/Scenario.ts`, который в
   `awake()` читает сцену через `this.context.assets.getAsset("scenes/main.scene.json")` и
   вызывает `SceneSerializer.deserializeScene`.
6. **ScenarioCreator**: писать `entryScene` в манифест, если файл сцены есть
   (`build-package.mjs`, рядом с `entryPoint`).
7. Собрать `npm run build -- --scenario <Name>`, загрузить через `/admin`, сравнить скриншот с
   вьюпортом редактора.

*Готово, когда:* `docker compose … up` поднимает каталог и редактор на одном порту, и сцена из
примитивов, света и камеры, собранная в `/editor/`, открывается в `/play/<id>` из ZIP от
ScenarioCreator и выглядит так же.

### Фаза 2 — доработки движка (2–4 дня, в WebEngineTS, параллельно фазам 3–4)

По правилам экосистемы каждый пункт сначала перепроверяется и заносится в
`.claude-shared/ENGINE-GAPS.md`.

| # | Что | Зачем | Статус |
|---|---|---|---|
| E1 | Загрузчик читает `entryScene`: импортирует все модули скриптов, десериализует сцену, догружает `pendingAssetGuids`, потом зовёт entry point | Убирает шаблонный код из `Scenario.ts` | Подтверждено: поле нигде не читается |
| E2 | Режим редактирования: не вызывать `awake`/`start`/`update` пользовательских скриптов | `GameObject.addComponent` зовёт `_systemAwake()` сразу (`GameObject.ts:269`), то есть скрипт выполнится прямо в редакторе | Подтверждено |
| E3 | Ссылка на меш из GLB (guid файла + локальный id) | Меш из `loadModel` создаётся через `Mesh._fromThreeGeometry` без guid и без рецепта → сериализуется как `null` | Подтверждено по коду; проверить на solar-system |
| E4 | `TypeRegistry`: замена класса при горячей перезагрузке | Новый класс с тем же именем сейчас отклоняется с ошибкой | Подтверждено |
| E5 | Стабильные guid для материалов в таблице сцены | Сейчас guid содержит `Math.random()` — каждый Save даёт новый diff в git | Подтверждено; не блокирует |

E2 нельзя привязать к `Application.isPlaying`: сценарии строят мир в `awake()` до старта цикла.
Нужен явный флаг.

### Фаза 3 — ассеты (≈1 неделя)

1. `FsAssetSource implements IAssetSource` поверх `FileSystemDirectoryHandle`; подключается через
   `Resources.useSource`.
2. Guid как в `ScenarioCreator/scenario-meta.mjs`: `sha256(id + NUL + path)`. Перенести функцию
   в TS и закрепить тестом на известных значениях — иначе сцена из редактора не найдёт ассеты
   в ZIP.
3. Настоящая панель Project вместо заглушки: дерево папки, превью текстур, импорт перетаскиванием
   файла (копия в `assets/`).
4. Перетаскивание: текстура → слот материала, GLB → сцена (зависит от E3).
5. Выбор ассета для полей `FieldType.Asset` с фильтром по `assetType`.

*Готово, когда:* сцена с текстурированной моделью собирается в ZIP и на платформе модель и
текстура на месте.

### Фаза 4 — генерируемый инспектор (≈1 неделя; это P3 общего плана)

1. Таблица «`FieldType` → компонент-редактор» (Number, Boolean, String, Vector2/3/4, Quaternion
   как углы Эйлера, Color, Rect, Bounds, Enum, GameObject, Component, Asset, Sprite, Mesh, Array).
   `Curve`, `Gradient`, `Bursts` — позже, пока только чтение.
2. Секция компонента строится из `getAllFields(ctor)`; учитывает `header`, `range`, `tooltip`,
   `displayName`, `hideInInspector`.
3. Удалить `BUILTINS`; «Add Component» строится из `TypeRegistry.all` + `category`.
4. Запись значения — через сеттер свойства (то же правило, что в `SceneSerializer._assign`).
5. Инспектор материала (общий материал из таблицы сцены редактируется один раз для всех).
6. Лазейка для ручных редакторов: реестр «typeName → свой Angular-компонент».

*Готово, когда:* `component-section.component.ts` не содержит ни одного имени компонента.

### Фаза 5 — скрипты (≈1 неделя)

1. Компиляция TS в браузере (esbuild-wasm, `experimentalDecorators: true`), модули грузятся из
   blob-URL с переписанными относительными импортами — как это делает `Scenario` при prelink.
   В Docker для этого нужна своя CSP на `/editor/` с `'wasm-unsafe-eval'` (§3).
2. Декорированные классы попадают в `TypeRegistry` → появляются в «Add Component», инспектор
   для них уже готов после фазы 4.
3. Слежение за `scripts/`: при изменении файла — снимок сцены, перезагрузка модулей,
   восстановление (зависит от E4; до него — перезагрузка страницы редактора с восстановлением
   проекта).
4. **Проверить в ScenarioCreator:** `build-package.mjs` запускает `tsc` с `--ignoreConfig` и без
   `--experimentalDecorators`, хотя в `tsconfig.json` он включён. Декораторы движка — старого
   образца `(target, propertyKey)`. Ни один сценарий их пока не использует, так что это не
   всплывало. Собрать скрипт с `@SerializedField`; если падает — добавить флаг.
5. Ошибки компиляции — в панель Console со ссылкой на файл и строку.

*Готово, когда:* `Orbiter` из solar-system, получив `@Serializable`, вешается на объект в
редакторе, его `radius` и `speed` правятся в инспекторе и доезжают до платформы.

### Фаза 6 — Play (3–5 дней)

1. Упаковщик в памяти: проект → ZIP (скомпилированные скрипты + `assets/` + манифест).
2. `play.html` в iframe: import map на `/assets/WebEngineTS.standalone.js` платформы,
   `new Application(canvas)`, `loadScenarioFromBuffer`. Платформа ставит
   `X-Frame-Options: SAMEORIGIN` — для iframe с того же origin это проходит.
3. Вкладка Game рядом со Scene; Play / Stop / Restart.
4. Консоль iframe → панель Console через `postMessage`.
5. Удалить `play-mode.service.ts` с его копией цикла.

*Готово, когда:* Play показывает то же, что платформа, и Stop оставляет сцену редактора
нетронутой (она в другом окне и не менялась).

Просмотр живых значений в инспекторе во время игры — отдельная задача после этой фазы.

### Фаза 7 — экспорт и публикация в каталог (3–4 дня)

1. File → Build: тот же упаковщик из фазы 6 отдаёт ZIP файлом.
2. **File → Publish**: ввод `ADMIN_TOKEN` (как в `/admin`, в `sessionStorage`), затем
   `POST /api/catalog` (строка создаётся неопубликованной, если её нет) и
   `POST /api/scenarios/:id/archive`. Ответ бэкенда показывается как есть: он называет точную
   причину отказа. Ссылка «открыть в `/play/<id>`» после успеха.
3. Проверка в редакторе до отправки: «каждый `type` из сцены есть в движке или в скриптах
   проекта». Остальное проверяет бэкенд.
4. Форма `scenario.meta.json` (id, название, описание, категория, версия). `id` — это slug в
   `/play/:id`, поэтому задаётся явно.
5. Релизные сборки (KTX2, LOD, стриминговый манифест) остаются за ScenarioCreator.

Публиковать строку сразу видимой студентам редактор не должен: переключатель публикации
остаётся в `/admin`.

Риск: два упаковщика (браузерный и `build-package.mjs`) могут разойтись. Страховка — скрипт,
который сравнивает манифесты обоих для одного проекта.

### Фаза 8 — перенос настоящего сценария (≈1 неделя)

Взять Molecules или статическую часть solar-system и перевести на сцену + компоненты. Это
проверка всего плана содержимым, которое видят студенты, и источник следующих пробелов движка.

### Фаза 9 — качество редактора (после, по потребности)

- Undo на diff'ах (`PrefabDiff` уже чистый модуль) вместо снимков всей сцены, лимит сейчас 30.
- Префабы в UI: создать из объекта, маркеры изменённых полей, Revert.
- Множественный выбор, перетаскивание в иерархии, поиск.
- Редактирование UI-канваса: гизмо для `RectTransform`.
- Вьюпорт через движок (`RenderTexture`, общий план §1.3). Пока вьюпорт рисует сцену сам, в нём
  не видно того, что обновляет `Application._loop`: линии, частицы, UI, LOD.
- Перенос оформления из `design/`.

## 6. Порядок и зависимости

```
Фаза 0 → Фаза 1 ─┬→ Фаза 3 (ассеты) ──┐
                 ├→ Фаза 4 (инспектор) ┼→ Фаза 5 (скрипты) → Фаза 6 (Play) → Фаза 7 → Фаза 8
                 └→ Фаза 2 (движок) ───┘
```

- Фазы 3 и 4 независимы друг от друга.
- E1 улучшает фазу 1, но не блокирует её. E2 блокирует фазу 5. E3 блокирует GLB в фазе 3.
  E4 блокирует только горячую перезагрузку.
- До конца фазы 7 — около 7–8 недель.

## 7. Чего в плане нет намеренно

- **Пользователи и роли в платформе.** Редактор работает с единственным `ADMIN_TOKEN`.
- **Хранение проектов на сервере** — до решения 6.

- **Вывод ScenarioCreator из работы.** Он остаётся релизным сборщиком; вопрос возвращается после
  фазы 8.
- **Канал параметров в сценарий** — отклонён в `WebEngineTS/design/scenario-parameters-decision.md`.
- **Встроенный редактор кода, WebGPU, совместная работа.**
